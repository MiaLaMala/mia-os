# Mia OS Frontend: Neubau auf Svelte, modulare Seiten

> **Auftrag von Mia (06.09.2026):** „alles neu aber komplett modulare seiten",
> Animationen global, Eigenbau-Elemente durch Libraries ersetzen,
> besonders der selbstgebaute Kalender.

**Ziel:** Das handgeschriebene Frontend (2447 Zeilen Jinja + CSS + JS) durch
eine Komponenten-Architektur ersetzen. FastAPI wird zur reinen JSON-API.

---

## Warum diese Wahl

| Baustein | Gewählt | Warum nicht anders |
|---|---|---|
| Rahmen | **Svelte 5 + Vite** | React braucht mehr Laufzeit-Code für dasselbe. Svelte kompiliert weg, das Ergebnis bleibt eine kleine statische Datei. |
| Router | **svelte-spa-router** | SvelteKit bräuchte einen Node-Server neben FastAPI. Zwei Server für eine Seite mit sechs Unterseiten lohnt nicht. |
| Stil | **Tailwind 4** | Ersetzt die 1500 Zeilen handgeschriebenes CSS durch Klassen, Design-Tokens bleiben in einer Datei. |
| Bausteine | **bits-ui** | Kopflose Komponenten (Dialog, Select, Schalter, Tabs) mit Barrierefreiheit eingebaut. Das Aussehen bleibt unseres. |
| Kalender | **FullCalendar** | Genau der Punkt, an dem mein Eigenbau schwach war. Monat, Woche, Tag, Liste, Ziehen und Ablegen. |
| Animation | **Svelte-Transitions + motion** | Eingebaut, kein Zusatzpaket für das meiste. |

**Kein CDN.** Alles wird gebaut und aus dem eigenen Container geliefert. Auf
einer Seite mit Ausweisen und Arztunterlagen wird nichts von fremden Servern
nachgeladen.

## Architektur

```
frontend/                 (neu, Build-Zeit)
  src/
    lib/
      api.ts              ein Ort für alle Serveraufrufe
      stores.ts           Zustand (Einstellungen, Thema)
      types.ts            Typen, aus dem Backend abgeleitet
    komponenten/          wiederverwendbar, EIN Zweck pro Datei
      Kachel.svelte
      Kennzahl.svelte
      Schalter.svelte
      Auswahl.svelte
      Chip.svelte
      Seitenkopf.svelte
      Ladebalken.svelte
      Leerzustand.svelte
    seiten/               eine Datei pro Seite, sonst nichts
      Uebersicht.svelte
      Termine.svelte
      Gesundheit.svelte
      Homelab.svelte
      Dokumente.svelte
      Einstellungen.svelte
    App.svelte            Rahmen, Navigation, Router
  vite.config.ts
  package.json

src/                      (bleibt, wird schlanker)
  main.py                 nur noch JSON + eine Route für die App
  web/static/gebaut/      Ergebnis des Builds
```

**Modular heißt konkret:** Jede Seite ist eine Datei, die nur ihre Daten holt
und Komponenten zusammensetzt. Keine Seite kennt die andere. Eine neue
Kategorie ist eine neue Datei plus ein Eintrag in der Routen-Liste.

## Etappen

Jede Etappe endet mit grünen Gates, einem Commit und einem Zwischenstand.
So überlebt die Arbeit einen Abbruch.

### Etappe 1: Gerüst und Werkzeug
- `frontend/` anlegen, Vite + Svelte 5 + TypeScript
- Tailwind 4 mit den Farbwerten aus DESIGN.md als Tokens
- Build schreibt nach `src/web/static/gebaut/`
- Dockerfile bekommt eine Node-Stufe
- **Beweis:** `npm run build` erzeugt Dateien, Container startet

### Etappe 2: Backend wird API
- Fehlende Endpunkte: `/api/overview`, `/api/events`, `/api/settings`
- Die sieben HTML-Routen fallen weg, eine Route liefert die App
- Tests auf JSON statt auf HTML-Schnipsel
- **Beweis:** jeder Endpunkt liefert die erwarteten Felder

### Etappe 3: Rahmen und Bausteine
- `App.svelte`: Navigation, Router, Seitenwechsel mit Übergang
- Grundkomponenten mit Animation
- **Beweis:** Navigation läuft, Übergänge sichtbar

### Etappe 4: Seiten, einzeln
- Übersicht, Gesundheit, Homelab, Dokumente, Einstellungen
- Jede Seite einzeln fertig und geprüft
- **Beweis:** Screenshot je Seite, Vergleich mit heute

### Etappe 5: Kalender auf FullCalendar
- Monat, Woche, Tag über die Library
- Farben je Kalender, Emojis raus, deutsche Beschriftung
- **Beweis:** alle drei Ansichten, Handy und Desktop

### Etappe 6: Animationen global
- Seitenwechsel, Listen gestaffelt, Zahlen zählen hoch
- Rücksicht auf `prefers-reduced-motion`
- **Beweis:** im Browser gemessen

### Etappe 7: Aufräumen
- Alte Templates und CSS löschen
- HANDOFF.md neu
- **Beweis:** alle Gates grün, CI grün, deployt

## Risiken

| Risiko | Umgang |
|---|---|
| Build-Schritt im Deploy | Node-Stufe im Dockerfile, der Pull-Deploy baut mit. Fällt der Build, bleibt der alte Container stehen. |
| Größeres Bundle als heute | Messen. Ziel unter 250 KB gepackt. FullCalendar allein wiegt rund 90 KB. |
| Editor (OnlyOffice) bricht | Die Editor-Route bleibt vorerst serverseitig, sie hängt an einem fremden Skript. |
| Turn-Abbruch mitten drin | Jede Etappe committen. Der Stand ist immer lauffähig. |
